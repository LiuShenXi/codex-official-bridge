## 服务链路

```text
主服务器二号 / 三号容器（host network，独立 SOCKS 用户密码）
  → socks5h://127.0.0.1:11082
  → codex-ip2-tunnel.service（main-server → BWH 专用 SSH）
  → BWH 127.0.0.1:10802
  → xray-ip2.service / egress-hw2
  → 新 qqpw VLESS + REALITY + Vision
  → 72.234.229.128
```

- BWH 原 `xray.service` 与 `/usr/local/etc/xray/config.json` 保持不变，原服务进程 PID 与配置 SHA-256 均与操作前一致。
- IP2 使用相同已安装的 Xray 26.3.27，但单独运行 `xray-ip2.service`，避免重启 IP1。配置 `/usr/local/etc/xray/ip2.json`，root:xray、0640，仅绑定 loopback:10802；有两个独立 SOCKS 认证用户。
- IP2 只有一个 VLESS 出站，没有 direct / IP1 回退出站；UDP 未启用。
- main-server 新增 `/etc/systemd/system/codex-ip2-tunnel.service`，仅绑定 loopback:11082，私钥与可信 known_hosts 在 `/opt/codex-ip2-tunnel/`（0700）。
- BWH 专用 SSH 用户 `codex-ip2-tunnel` 的公钥设置 restrict + port-forwarding，仅 permitopen 127.0.0.1:10802。
- 两个新服务均 enabled / active，自启和断线重连已配置。
- 仅 account-2、account-3 私有 `.env` 中 `BRIDGE_EGRESS_PROXY` 改为各自认证的 IP2 SOCKS 地址；沿用现有 Compose 引用，重建这两个容器应用环境。未修改 auth.json、网关 Key、模型配置或 Sub2API 的上游地址。
- `cloudbrowser-tunnel`、原一号网关、聊天镜像和既有 BWH IP1 入口均保持原设置。Sub2API→主服务器的 `codex-bridge-tunnel` 与本次主服务器→BWH的 `codex-ip2-tunnel` 是两条职责不同的隧道。

VLESS UUID、REALITY 参数、SOCKS 密码和 SSH 私钥只保存在私有服务配置中，不写入常驻记忆或此文档。配置字段参考 [Xray VLESS](https://xtls.github.io/config/outbounds/vless.html) 与 [SOCKS 入站](https://xtls.github.io/config/inbounds/socks.html)，并以已安装二进制的配置验证和真实握手结果为准。

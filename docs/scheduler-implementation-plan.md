## 1. 目标、范围与阅读顺序

交付框架自身的共享账号池调度：每个任务稳定落在一个合格账号上，忙时有序等待，失败时行为明确，并能解释为什么这样调度。脱离 Sub2API、CPA 和管理后台也能运行与管理。

已确定沿用现有 Node + native Rust runtime；Agent、工具和项目文件仍在客户端。不再重开“替换成完整官方 app-server”的架构选择。保持任务/身份/出口稳定、生成受控、请求保真；不得把官方库复用或测试通过宣称为账号风险降低的证据。

依次阅读，遇到冲突先核对代码与证据并修正文档，不自行放宽规则：

1. 本文件：实施顺序、完成条件与交接约束。
2. [调度主设计](scheduler-design-v1.md)：目标、不变量、组件、队列、账号资格和阶段。
3. [状态与控制合同](scheduler-control-contract.md)：来源、发送许可、取消、交付障碍与恢复。
4. [出站一致性合同](scheduler-fidelity-contract.md)：A→B、官方直连C↔B、调度前后B0→B1对照。
5. [现有架构](architecture.md)、[构建说明](native-build.md)、当前源码和适用 AGENTS.md。
6. [独立原型报告](../../codex-bridge-scheduler-validation/validation/REPORT.md)及[复现入口](../../codex-bridge-scheduler-validation/validation/README.md)：证据与可移植测试思路，不是生产实现。

完整开发范围为 **M0–M3：接入合同、持久内核、HTTP/WS 正式通路、管理 CLI/API、故障恢复、保真与独立运行验收**。M4 图形后台、分布式多协调器、跨账号上下文迁移、精细充值计费均后做，不阻塞本轮。

本清单管理执行，不重复定义另一套技术规则；必要的设计修订回写对应合同。实现者应持续推进所有不受阻的开发项，不在每个阶段结束后重复询问是否继续。真正改变已确定目标的取舍才需要用户决定。

- [ ] **M2.2 发送闸门。** DB提交发送许可先于网络发送；重复许可只消费一次；发送与撤销原子排序。每个401恢复attempt仍受闸门控制，中间401不释放逻辑lease。
- [ ] **M2.3 WS握手与逐轮准入。** 101前身份/来源/绑定/连接预算；每个response.create含预热都取得执行许可；新turn重查权限，未知生成消息不能绕过。
- [ ] **M2.4 独立observer与delivery。** HTTP/WS上游reader独立于下游；响应归属与终态在完整交付前持久确认；原始压缩片段和WS消息不重编码。生成、上游观察、下游连接和缓冲分别计量。
- [ ] **M2.5 取消、慢读、断线。** 未发送可靠撤销；可能已发进入有界观察；无终态保留DEBT。已完成但交付中断保留delivery_unconfirmed，不能再次生成补答案。
- [ ] **M2.6 重启与事件恢复。** 未ACK关键事件有界保留；旧代际证据结算原lease，旧许可不能新发；重复/乱序/冲突事件明确处理。ACK丢失不能复活已经释放的债务。

- [ ] **M2.9 资源封顶。** raw body、解码副本、最大WS帧/SSE事件、delivery队列、detached observer、401缓存、outbox及许可防重放记录都计预算；耗尽明确拒绝/收尾，不无限增长。

**完成门槛：** 使用正式编译的Rust worker运行控制合同第8节全部适用测试；覆盖PREPARE/COMMIT/revoke竞争、双向慢读、大压缩事件、终态ACK丢失、401中断以及实际进程死亡。HTTP与WS不得有第二套计数或旁路；一个未知任务不影响其他仍满足预算的任务运行。
